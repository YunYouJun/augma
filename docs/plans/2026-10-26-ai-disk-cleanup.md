# AI 磁盘清理实现计划

日期：2026-10-26。状态：方案与基础验证完成；Homebrew 首个增量已实现，其余里程碑待完成。

目标：在 Augma 中完成“看懂占用 → 制定清理计划 → 确认具体操作 → 核对空间变化”的流程。优先解决开发者 Mac 上旧安装包、构建缓存和工具缓存占用的问题。

## 实现方向

采用 **本地扫描与规则判断 + AI 排序和解释 + 固定执行接口**。AI 可以理解“希望腾出 20 GB，尽量不影响当前开发”等意图；可操作对象、风险、容量与执行方式均由本地程序确定。

AI 入口已对齐 [DSH 默认运行时计划](./2026-10-26-dsh-runtime-goal.md)：新配置使用 DSH / Magpie，已有 DeepSeek 配置保留为显式兼容后端，不引入额外本地模型下载。断网或未配置模型时，本地扫描、排序、预览与手动清理仍然可用。

### 整机能力的实现决策

2026-10-26 补充：基础清理与原生体验保留在 Augma，Mole / Purge 不作为必装依赖。根据后续的可选安装与 AI 工具调用需求，增加[可选清理引擎与 AI 清理方案](./2026-10-26-cleanup-plugins.md)：优先验证 Mole CLI 的可选后端；Purge 作为原生扩展候选，需要先形成可用的工具接口。已接入的 Homebrew 官方接口继续保留，作为一个专项来源。插件与多步 AI 执行仍待实现。

Mole 的原生 Mac 应用当前为一次性 19 美元，官网同时明确 CLI 仍免费开源，因此收费本身不是 CLI 接入的阻碍。选择自主实现主要是为了控制原生体验、扫描预算、规则与分发依赖。来源：[官网价格与 CLI 区别](https://mole.fit/#faq)。Mole 公开仓库使用 [GPL-3.0](https://github.com/tw93/Mole/blob/main/LICENSE)；本项目的实施约定是独立编写代码，不复制、逐行翻译或打包其实现与整套规则库到当前 MIT 源码中。未来如确需复用其源码，再单独评估许可与分发安排。

可借鉴的行为设计：目录逐级下钻、按体积排序、分类预览、保护/忽略名单、完整性状态、重建成本说明与操作回执。先把需要的行为写成 Augma 自己的规格和验收样例；路径规则依据 Apple、Xcode、Homebrew、Docker 等官方资料逐项建立和验证。

后续优先交付的原生增量：

1. **只读占用概览**：以用户选择或已授权的根目录为范围，统计大目录与大文件，提供下钻、Finder 定位、进度、取消和无法读取的范围。容量大仅表示值得检查，不表示可删除。此阶段不加入通用删除按钮。
2. **有依据的分类规则**：先扩展旧安装包、已验证的开发缓存，再逐个接入工具官方清理接口。区分可重建缓存、需人工检查的资料和仅可查看的系统内容；仅靠目录名或时间不生成可执行结论。
3. **AI 制定清理计划**：复用现有匿名摘要与受限响应，只建议顺序、理由和目标；候选身份、容量和动作由本地确定，保留逐项确认及结果核对。

“整机”表示对可访问范围提供统一概览，不表示绕过 macOS 权限。系统目录、其他账户、权限不足和未扫描的部分明确标注；不把“无法读取”显示为零占用。后台无扫描请求时不创建常驻扫描器或轮询任务。

没有在本次调研中找到适合直接嵌入当前 SwiftUI/MIT 项目、同时覆盖所有来源的统一清理 SDK。建议组合 macOS 文件接口、来源工具的官方命令及可选扫描器，具体证据见[复用方案调研](./2026-10-26-ai-disk-cleanup-research.md)。

## 当前工作区已有能力

以下是现有代码的能力，不代表本计划已经实现或相关改动已经发布：

- `SystemCleanupScanner`：扫描 Downloads 顶层 dmg/pkg/xip，以及 Xcode DerivedData；仅列出至少 7 天未修改、完整检查的候选。当前共享预算为 50,000 个条目、8 秒、最多 100 个候选。
- `SystemCleanupStore` / `SystemCleanupView`：显式扫描、逐项选择、Finder 定位、确认移入废纸篓、取消与失败反馈。
- `CleanupAdvice`：复用统一原生运行时，以匿名数字摘要生成类别建议，校验响应结构和已知编号；模型结果不会自动勾选或执行。
- 2026-10-26 执行现有 `SystemCleanupTests`：11 项通过。覆盖范围包含路径变化、符号链接、过期候选编号、扫描限额、取消、匿名摘要、模型回复校验和面板渲染。

需要补齐：目录占用概览、可扩展扫描来源、逐项推荐证据、空间口径、真实操作回执，以及开发工具官方清理接口。现有元数据复查属于尽力校验，不应描述成跨扫描与执行的原子保证。

## 产品流程

1. **查看占用**：显示当前可用空间、统计时间、分类大小，以及未读取或尚未检查的范围。
2. **选择扫描范围**：默认使用已支持的来源；额外项目目录由用户选择。快速扫描先出结果，深入扫描可单独启动、显示进度并取消。
3. **生成计划**：支持“优先低影响”“先看大项目”“尽量达到指定空间目标”。每项展示来源、规则依据、容量估算、重建代价和执行方式。
4. **确认具体操作**：可恢复文件操作与不可恢复的工具清理分开展示；确认内容绑定本次扫描和具体对象。AI 推荐与用户最终选择分别保存。
5. **查看回执**：列出完成、跳过、失败和原因；重新读取同一卷的可用空间，并提供查看废纸篓或工具结果的入口。

菜单栏先提供紧凑入口与扫描状态；详细列表继续放在原生清理面板中。磁盘与内存采用独立区域，不将“退出应用释放内存”计入磁盘清理收益。

## 第一批来源与边界

| 来源 | 第一阶段能力 | 执行方式与限制 |
| --- | --- | --- |
| Downloads 中的旧安装包 | 沿用现有扫描，增加年龄、大小和规则说明 | 用户逐项确认后移入废纸篓；“旧”不等于已经安装或不再需要 |
| Xcode DerivedData | 沿用现有扫描，补充构建活动提示和重建代价 | 可恢复路径优先；7 天未修改不等于无人使用，不涉及 Archives、设备备份或其他 Xcode 数据 |
| Homebrew 缓存与旧版本 | 第二里程碑加入，先做官方 dry-run 与能力检测 | 使用本机受支持版本的固定命令；无法稳定确定范围时仅展示预览，不启用应用内执行 |
| 用户选定的开发目录 | 后续增加只读占用排行 | 先标注 `.build`、构建输出等候选，不因目录名匹配就批量删除；不递归默认扫描所有仓库 |
| Docker | 后续只读展示用量与 build cache 候选 | 使用官方接口；运行中资源、数据卷和容器可写层不进入首版清理范围 |
| 重复文件 | 后续可选 Czkawka 扫描 provider | 仅扫描用户选择的目录；相同内容不代表相同用途，始终由用户决定保留哪份 |

不进行通用的 `~/Library/Caches` 全量清扫。个人文档、照片库、备份、钥匙串、源代码、应用数据和包管理器的共享 store，不因“体积大”“时间旧”自动获得可删除结论。

## 容量统计与实际释放

必须分别保存并展示以下数字：

- **候选大小**：逻辑大小和本地可取得的分配大小，明确统计完整性，避免同一文件或父子目录重复计数。
- **预计可释放量**：估算值，可为未知；不能把分配大小简单相加后承诺为实际收益。硬链接、APFS 共享数据、快照及正在使用的文件都可能影响结果。
- **实测可用空间变化**：同一卷、相同 API 口径在操作前后的读数差，可为零或负数；其他进程可能同时写入，因此不能全部归因于本次操作。

macOS 提供不同用途的卷可用容量 API，界面需要标注口径，不能混用为同一个精确数字。参考 [Apple URLResourceValues](https://developer.apple.com/documentation/foundation/urlresourcevalues)。

**移入废纸篓不等于释放空间。** 对这类动作显示“已移入废纸篓”，由用户在 Finder 检查和清空。首版不清空整座废纸篓；工具管理的缓存清理若永久移除数据，需要单独说明无法恢复和重新下载/构建的成本。参考 [Apple 磁盘空间说明](https://support.apple.com/en-us/102624)。

Time Machine 本地快照由系统随空间需求管理，本计划仅解释统计差异，不将删除快照作为默认优化。参考 [Apple 本地快照说明](https://support.apple.com/en-us/102154)。

## 代码结构与数据契约

以当前 `SystemMonitor/Cleanup/` 为增量入口，避免同时重写监控、助手或主窗口：

- **扫描来源**：抽出 `CleanupProvider`，统一来源能力、扫描预算、进度、候选与不完整原因。安装包和 DerivedData 先迁入，保持现有行为。
- **本地计划**：增加 `CleanupPlan` 与规则评估，管理扫描版本、来源、对象身份、风险、原因、动作类型与预算。来源规则是版本化代码，不能由模型或远程文本修改。
- **模型建议**：扩展 `CleanupAdvice`，只接受当前扫描中的匿名候选 ID、允许的理由和推荐顺序。空间合计、风险、路径和命令由本地生成或验证。
- **执行与回执**：抽出执行入口，接收已经确认的本地计划，按来源重新验证后执行并返回 `CleanupReceipt`。回执记录规则版本、逐项状态、时间与容量读数；路径只保存在本机。
- **视图状态**：继续由 `SystemCleanupStore` 负责扫描、预览、确认、执行、核对的状态转换与取消；视图不拼接命令、不直接删除文件。

动作能力至少区分：`reviewOnly`、`moveToTrash`、`toolManagedCleanup`。模型不能把只读来源升级为可执行来源，不能降低本地风险等级，也不能提供新的文件路径或 shell 片段。

CLI provider 使用绝对可执行路径和独立参数数组，避免 shell 拼接；检测工具版本、配置位置和本地/远程上下文，设置超时及输出上限。工具更新、范围变化或预览无法复现时应重新生成计划。dry-run 只是预览，不能被当作最终操作的原子事务。

用户选择目录时保存必要的访问范围；如后续启用 App Sandbox，再按系统机制管理 security-scoped bookmarks。TCC 与文件权限失败需要明确展示，不能显示成“没有可清理项”。参考 [Apple 文件访问说明](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)。

### M1：把现有能力做成完整的清理计划流程

- [ ] 增加扫描总览、来源摘要、扫描时间和不完整原因。
- [ ] 将旧安装包与 DerivedData 抽为独立 provider，支持分来源预算，避免一个来源耗尽全部扫描额度。
- [ ] 增加可恢复动作的本地计划、逐项依据、重建代价和过期检测；保留默认不勾选。
- [ ] 扩展 AI 建议到匿名候选级别；本地规则排序作为离线回退。
- [ ] 增加操作回执和同卷空间复测，准确区分“移入废纸篓”和“可用空间变化”。
- [ ] 在菜单栏与系统监控中提供清晰入口；更新中英日文文案。

完成标准：用户无需 AI 也能完成扫描、预览、确认、移入废纸篓和核对结果；AI 建议仅改变推荐信息。不能承诺“移入 10 GB 就释放 10 GB”。

### M2：接入能实际清理开发工具缓存的官方接口

- [x] 首先接入 Homebrew 的只读检测和 dry-run，完成受支持版本的输出契约与 fixture。当前验证 7.x，未知格式只预览；原始报告不传给 AI。
- [x] 增加单独确认的固定清理动作，禁用自动 `autoremove`；执行前复查版本和预览。检测到可能覆盖该选项的 `brew.env` 时只预览。
- [ ] 对所有工具动作增加超时、取消、部分成功、版本变化和范围变化处理；不可恢复动作与废纸篓动作分开确认。
- [ ] 按工具自身统计与卷容量分别记录结果，不将终端输出直接当作精确的实际释放空间。

完成标准：支持的 Homebrew 版本可以预览具体影响，再由用户确认执行；未知版本或范围不清晰时回退为预览和官方说明。

首个增量补充：已接入 45 秒超时、256 KiB 输出上限、预览取消、五分钟有效期、失败回执和卷可用空间差值。Homebrew 默认 `cleanup` 也可能执行自动依赖移除，必须设置 `HOMEBREW_NO_AUTOREMOVE=1`；`brew.env` 可覆盖传入环境变量。其内部部分失效下载清理不出现在 dry-run 中，界面和确认框明确说明这是按来源规则执行，不能称为逐文件锁定的计划。依据：[官方命令与环境变量](https://docs.brew.sh/Manpage)、[cleanup 实现](https://github.com/Homebrew/brew/blob/master/Library/Homebrew/cleanup.rb)、[环境配置加载](https://github.com/Homebrew/brew/blob/master/bin/brew)。

验证：原有 11 项清理测试及新增 10 项 Homebrew 测试通过，包含本机 Homebrew 只读预览；子进程测试覆盖双输出流、非零退出、超时、输出上限和取消。执行动作先使用假执行器验证，随后在人明确确认后，通过真实应用内的 Homebrew 7.x 流程完成清理，命令成功返回，空间变化回执正常显示。清理期间面板关闭和正常退出会等待操作完成，预览没有常驻进程。

界面验收：已通过 `./script/build_and_run.sh --verify` 构建启动，在真实应用内打开系统监控 → 清理磁盘与内存 → Homebrew 预览，核对条目数、容量估算与原始报告入口；先验证了确认框取消，再在人明确确认后刷新同一范围的预览并执行，核对成功回执。此次授权及实际执行仅覆盖 Homebrew 管理的内容，不包含个人文档、Downloads 安装包或其他整机目录。

## 验证与验收

所有破坏性测试仅针对临时目录或注入的假执行器，真实用户目录只做用户主动触发的读取与验收。

- 扫描：符号链接、目录替换、跨卷、权限失败、iCloud 占位文件、硬链接、父子重叠、超时与取消；结果不完整时不生成完整收益承诺。
- 计划与执行：旧扫描 ID、确认后内容变化、扫描与执行之间的路径替换、部分失败、重复点击、清理中关闭窗口、重启后回执可读。
- 模型：未知 ID、额外字段、超长回复、指令注入文本、命令/路径字段、伪造容量或风险，以及取消后的迟到回复。
- 工具：未安装、不支持版本、远程 Docker 上下文、异常输出、语言环境差异、无权限、超时、预览到执行之间的状态变化。
- 结果：移入废纸篓后空间不变、工具报告与卷读数不一致、外部并发写入、空间读数不可取得；不产生虚假的“已释放”提示。
- UI：480/700 宽度、深浅色、长文件名、键盘操作、动态状态和 VoiceOver；复用现有原生渲染验证方式。

基础验证命令：

```sh
swift test --package-path apps/mac --filter SystemCleanupTests
```

真实 macOS 渲染与启动沿用仓库的 SDK 链接参数和 `./script/build_and_run.sh --verify`。当前计划不新增定时扫描或后台清理任务。

## 复用决策

- 首选：系统文件 API、现有 SwiftUI/原生 AI 运行时链路、来源工具的官方预览/清理能力。
- 可选：固定版本的 MIT Czkawka CLI，仅作为扫描来源；不引入完整 GUI，也不直接采用其自动删除选项。
- 参考：Lemon Cleaner 和 Mole 的来源分类与交互设计。当前公开许可证有 GPL 约束，与本仓库 MIT 代码的复制、链接或再分发需要分别评估；本计划不直接移植其代码或打包其清理脚本。
- 整机能力：按上面的可选引擎方案推进；原生流程与 AI 复用同一个 interface。Mole 免费 CLI 为可选后端候选，Purge 为原生扩展候选，均不设为必装依赖，也不依赖 Mole 付费桌面应用。
- 外部依赖落地前记录版本、commit、许可证、通知文件与分发方式，避免把持续变化的 `main` 当作已验证依赖。
